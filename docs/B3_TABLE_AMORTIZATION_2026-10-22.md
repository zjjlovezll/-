# B3 接触表按反演批次摊销（2026-10-22）

问题：接触表（`src/velch/contact_map.py`，单次查表 8.46 µs vs 直算 154.2 µs）此前被判"摊销 1:40、不划算"。
本项用**实测调用计数**重算，并检查跨工况的表格复用率。

## 1. 实测调用模式（`validation/crh380a_m/probe_table_amortization.py`）

在进程内包装 `velch.vehicle_solver.find_strip_contact`（**不是** `velch.contact` 的绑定，
否则包装不生效——历史坑），记录每个 `(lower_s, upper_s, roll)` 单元格的调用次数。
辙叉窗 0.05 s，`case_frog_N_strip05.json`：

| 量 | 实测 |
|---|---|
| 墙钟 | 14.2 s |
| 接触搜索调用 | **97 736 次** |
| 不同单元格 | **125 个** |
| 每单元复用 | **781.9 次** |

原判"1:40"假设每单元只用 ~4 次；实测每单元被用 **782 次**（同一站位在同一 run 内被上千个内部步反复访问，
roll 只有 60 余个离散取值）。因此**单个 run 内建表就已经划算**。

## 2. 批次摊销（实测单价 × 实测调用数）

单价：直算 154.2 µs、查表 8.46 µs、建一个单元格 23 ms（均为既有实测，见 `docs/CONTACT_MAP_2026-10-21.md`）。

| 反演批内次数 | 直算 s | 建表+查表 s | 加速 |
|---|---|---|---|
| 1 | 15.07 | 3.70 | **4.07×** |
| 5 | 75.35 | 7.01 | 10.75× |
| 10 | 150.71 | 11.14 | 13.52× |
| 20 | 301.42 | 19.41 | 15.53× |
| 50 | 753.54 | 44.22 | 17.04× |

上限 = 154.2 / 8.46 = **18.2×**（建表 23 ms × 125 = 2.9 s 是固定成本）。

## 3. 跨工况复用率（关键前提）

批次摊销要求"参数变了但单元格不变"。用 C 变化 **+1 %**（`effective_radius_m` ×1.01）的变体验证：

| 量 | 基准 | 变体 |
|---|---|---|
| 接触调用 | 97 736 | 97 267 |
| 不同单元格 | 125 | 125 |
| 单元格集合 Jaccard | — | **1.00**（125 全部共享） |

⇒ 在反演常见的 1 % 量级参数扰动下，`(站位, roll)` 单元格集合**完全重合**，建表成本可整批共享。
（若参数扰动大到轨迹显著改变，如 >10 % 刚度变化导致 roll 分布移动，需按 roll 分箱重建——这一点尚未实测，
如实标注为未验证边界。）

## 4. 结论与建议

1. 表**应当**接入反演/批处理路径：单个 run 4.07×、10 次批 13.5×、50 次批 17.0×（上限 18.2×）。
2. 接入形态：按 `(站位, roll 分箱)` 建表并跨 run 缓存，缓存键必须含**曲面标识**（历史教训：
   键漏曲面标识曾导致 6 036 kN）。
3. 单次"看一个工况"的交互式使用**不必**建表（建表 2.9 s > 单 run 的接触总时长差），保持直算。
4. 与 B1 独立：B1 抬步长上限后调用次数下降 7.5×，会让建表固定成本的占比上升，两者叠加时：
   步长放大到 7.5e-4 + 建表 → 单 run ≈ 0.5 + 2.9 s，此时表只在 ≥2 次批时才有意义。**叠加效应尚未实测**，
   列为待办。
